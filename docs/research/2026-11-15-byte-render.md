# 第9阶段：大图渲染加速，保留相同RGB8结果

本阶段优化12／13号研究引擎的满强度渲染路径：在GPU完成既有裁切、乘255、舍入及RGB8转换，再传回CPU，减少浮点图像传输和CPU数组操作。分块仍为128行，坐标、采样、模型、浮点精度和非有限值检查保留。没有训练模型、降低尺寸或跳帧。稳定主版1.3未改动。

图片／视频产品流程仍先得到满强度RGB8，再混合用户强度并执行手动调整；直接调用研究渲染器的非满强度路径保留原计算。第8阶段已验证的固定对齐映射不走这条神经渲染路径。

## 同过程交替测量

现有RTX4060 Laptop、float32模型，6张已用照片构造6种尺寸，每种尺寸预热后新旧交替各6次。以下为独立重测的中位数，仅含准备好的映射应用到图像与传回CPU，不含模型分析、文件解码、手动微调、编码或界面。

| 尺寸 | 原13号渲染 | 新13号渲染 |
|---|---:|---:|
| 256×256 | 6.76ms | 7.06ms |
| 640×360 | 17.11ms | 10.48ms |
| 1920×1080 | 93.67ms | 39.88ms |
| 1917×1081 | 95.92ms | 40.19ms |
| 1080×1920 | 113.40ms | 55.88ms |
| 2160×3840 | 368.38ms | 143.17ms |

12号App8同样6种尺寸逐像素一致；1080p约96.36→39.26ms，4K约379.57→150.92ms。每个模型的各次输出均与原浮点传输／CPU转换公式逐像素相同。这里是同图反复计时，不是多张独立画质样本；大尺寸由照片放大，用于性能而非真实4K画质评价。小图没有稳定收益，不能称所有输入都更快。

此前分块诊断还记录了真实2160×3840视频帧及其缩放裁切版本。增大分块只能部分改善，且增加显存，因此本次没有改变默认分块。初次RGB8实验使用256行，不能把其速度当作最终128行产品结果。首次接入计时与回归测试并行，未用于上表；上表来自回归结束后的独立重测。没有控制全部外部系统负载或GPU时钟。

## 一致性和回归

- 12／13号两个实际检查点，各6种尺寸的GPU结果与原满强度CPU公式差0，包含奇数边、横竖图。
- 三项新CPU检查覆盖分块一致、非有限值在量化前被拒绝、无效分块参数拒绝；单独审查复跑通过。
- 全部Python280项通过，37.261秒；实际HTTP的PNG、普通MP4、有声微调MP4与第8阶段的文件哈希完全一致，零／半强度、手动微调、取消及活动导出停止防护通过。
- 独立只读审查未发现阻断项。此阶段没有重复浏览器视觉验收；HTTP图片和文件哈希一致不当作新的浏览器显示延迟测量。

**仍未达到1080p完整视频30fps。** 单是本次1080p渲染中位数已超过33.3毫秒，另有逐帧分析与编解码开销；不能用控件跟手或更快渲染宣称端到端实时。色彩语义和自然画面协调性也没有因本阶段自动提升。
