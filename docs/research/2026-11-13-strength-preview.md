# 强度拖动连续预览

适用于13号研究新版。保持手动微调为默认值时，强度拖动可使用页面内混合，后端继续生成最终预览。用户本机反馈为“能连续更新，比较跟手”。原版入口和稳定程序不改变；本阶段不宣称基础／HSL／曲线都已即时化。

## 为什么这样改

10次直接缓存校验及编码的剖析总计2.508秒，其中文件SHA计算及读取累计1.868秒、PNG约0.224秒，约占完整口径的75%和9%。该剖析的缓存颜色结果是人工占位，证明的是校验／编码开销，不是模型质量或浏览器延迟。

不通过削弱校验来提速。新流程在首次预览时获取后端已校验的原图与满强度RGB结果；页面只对这份固定像素做与后端相同的强度混合。每个动画回调读取最新状态，多个输入合并；匹配当前设置的后端响应仍是最终结果。

基础、HSL或曲线存在有效微调时回退原有后端链路。切换素材、映射或代次清除旧数据；解码迟到不能画到新素材，接口失败也会清除本地数据并保留已有画面。PNG解码／Canvas不可用时继续使用后端预览。项目保存和导出依旧校验素材、解码器及颜色网格。

## 验证结果

| 检查 | 结果 | 范围 |
|---|---|---|
| 65,536种通道值组合×101档整数强度 | RGB最大差0，共19,857,408个RGB通道值；另检查alpha | Python与Node数值，不是浏览器显示测量 |

| 新版缺少快速模块时的应用流程 | 13项通过 | 使用控件组件mock的初始化、上传、导出、保存等流程 |
| 原前端检查 | 22项通过 | 其中生命周期测试使用控件mock，不等于视觉操作验收 |
| Python研究检查 | 160项通过 | 新预览数据与普通预览一致，无效标记与损坏缓存拒绝 |
| 真实GPU／HTTP | 通过 | 满强度数据独立于微调；PNG、视频、有声半强度微调导出及取消保持正确 |
| 输出回归 | PNG、普通短片、有声微调短片SHA与前阶段一致 | 不是仅凭平均误差判定未改变导出 |
| 本机实际试用 | 用户确认“能连续更新，比较跟手” | 默认微调下的强度拖动；非自动计时 |

960×640像素混合核在Node中约3–5毫秒，**不包含**浏览器图像解码、Canvas PNG编码或绘制，不能当作实际画面延迟或帧率。没有可用的本机浏览器自动控制接口，本阶段没有自动视觉／逐帧拖动测量。

扩展原前端检查时发现旧测试夹具缺少现有`window.manualControls`接口，13项在初始化时失败；已确认页面与夹具此前在HEAD中都未改动。仅补齐生命周期mock后重跑原断言，22项通过，没有跳过检查或修改产品页面来迎合测试。
